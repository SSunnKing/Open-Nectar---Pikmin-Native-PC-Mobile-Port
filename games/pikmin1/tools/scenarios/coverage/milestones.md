# Slice: first-of milestones and progression

Paths are relative to `games/pikmin1/`. Every `file:line` pointer was checked against 3c7d100b (after the scenario integration branch merge) and carries its function name, which is the stable pointer if a number drifts. Verified items: see the verification log in [README.md](README.md).
Tier: **S** = runs on stand-in assets (CI); **D** = needs the disc tier (local, `_disc` tests); **S+** = stand-in with the named extra asset.
Effort: S small, M medium, L large. Risk = how likely a port change or mod breaks it unnoticed.
Covered = by an existing scenario (boot_smoke, throw_release, day30_clock, sprout_landing, onion_skip, objects_smoke, container_menu, extinction, captain_death, captain_damage, ship_parts, onion_unlock, onion_unlock_whistle, day_end, day_end_day29, extinction_day30, tutorial_skip, tutorial_firsts, tutorial_day1, pellet_table, ufo_part_discovery, pellet_carry, ship_part_carry, nectar_growth, bomb_firsts, carry_blocked, pikmin_cap, pikmin_cap_1, pikmin_cap_250, pikmin_cap_999, day_clock, demo_timers, whistle_gather_release, whistle_pluck_held, enemy_kills).

## 0. Facts that shape every scenario here

- `playerState` is a global; all progress is public fields: `mDemoFlags` (`isFlag/setFlag/setFlagOnly/resetFlag`, `Demo.h:15-53 (EDemoFlags)`, `DEMOFLAG_COUNT = 32+30+1`), `mContainerFlag` (`hasContainer`, `hasBootContainer`), `mResultFlags`, `mCurrParts`, `mRequiredUfoPartCount`, `mShipUpgradeLevel`, `mShipEffectPartFlag`, `mStagePartsCollected[]`, `mIsTutorialMode`, `gameflow.mPlayState.mCourseOpenFlags`, `gameflow.mGamePrefs` (challenge open flags), `gameflow.mWorldClock.mCurrentDay`. A scenario can read and write these with no input.
- The scenario runner starts the sandbox stage with no `id` line = `STAGE_TESTMAP` (=5, `GlobalGameOptions.h:35-43 (StageID)`). Consequences:
  - `isTutorial()` is false there (`playerState.cpp:603-621`: stage != Practice), so every `if (isTutorial())` branch (red Onion boot, 15th pluck text, Approach-seed, tutorial skip, clock freeze) is NOT exercised by default. A scenario can force `mIsTutorialMode`, but `isTutorial()` also needs `mCurrentStage->mStageID == STAGE_Practice`. A stand-in stage with `id` = Practice would be needed (see gap G1).
  - `getUfoParts` does `mStagePartsCollected[mStageID]++` (`playerState.cpp:1210`) with `u8[STAGE_COUNT=5]` and stage id 5: one-byte out-of-bounds write on the sandbox (lands in `mPerHourGraph.mStartTime`). Harmless in practice but a real latent bug the first part-collect scenario will touch; a `stage` id line in the sandbox fixes it.
  - Stage-gated triggers (`demoInvoker.cpp:39 (Navi::demoCheck)/49/60/85`, `workObject.cpp:827 (HinderRock::update)`, `pelletState.cpp:281 (PelletGoalState::init)`, `playerState.cpp:1215 (PlayerState::getUfoParts)`) check `mStageID == STAGE_Practice/Forest/Cave`. They need a stand-in stage with that `id` (gap G1) or are driven by setting the flag directly.
- `PlayerState::getUfoParts(id, isInvisible)` (`playerState.cpp:1149`) is a public entry that runs every part effect with no Pellet, no carry, no cutscene, if the part is registered (`UfoParts` come from `pelletMgr->registerUfoParts`, `pelletMgr.cpp:1517`; the stand-in `pelAnim.bin` registers 16 of the 30; the rest abort with `ERROR("sorry")` unless `isInvisible=true`). So the logic of all 30 parts is testable by passing `isInvisible=true`.
- Persistent side effects to isolate: `pc_achievement_unlock` writes `pikmin_achievements.txt` into the process cwd (`pc_achievements.cpp (save; pc_achievement_unlock)`). In a scenario run it now goes to the run's own `NECTAR_SAVE_DIR` (`filePath()`, added for onion_unlock), so nothing reaches the data dir and parallel runs start empty. `pc_achievements_load` is still cached (`sLoaded`), so state leaks between cases in one process: a scenario that needs an achievement unlocked twice needs two processes (why onion_unlock_whistle is its own scenario).
- Settings are neither read nor written in scenarios (README), so the cheat gates in `pc_achievements_blocked_reason` (`pc_achievements.cpp:154-166`) are at defaults. Tests of the gate need `pc_settings_scenario_set_*` hooks (`infinite_day` and `whistle_pluck` have one: `pc_settings.h`).
- Cutscenes: the stand-in tree has `demo60` (post-extinction) and `demo06` (blue Onion) only (`standin-cinema.md`). `DemoFlags::setFlag` (`gameDemo.cpp:259-307`) starts a movie whenever the flag has a movie index; with no `.cin` the movie plays as a zero-length movie and ends on its first update, with no abort (verified, see `terminals.md` section 2), but every event key it would carry (Onion boot, text, `MOVIECMD_*`) is lost. Anything that calls `setFlag` (not `setFlagOnly`) needs that demo's stand-in `.cin`, or the scenario pre-sets the flag with `setFlagOnly` and asserts the downstream state.
- Movie/text mapping source of truth: `registerDemoFlag` table `gameDemo.cpp:71-111 (DemoFlags::DemoFlags)` (flag -> movie index). Movie ids -> `cinemas/demoNN.cin`: `moviePlayer.cpp:37-97 (movieTitles)`. Text windows: `ogScrTutorialMgr::TUT_*` (`include/zen/ogTutorial.h:25-66 (EnumTutorial)`), opened via `MOVIECMD_TextDemo` (`newPikiGame.cpp:3219-3290 (GameMovieInterface::parse)`).

### The tutorial stage and its findings (2026-10-28)

G1 is closed for Practice: the stand-in tree has `stages/practice.ini` (the first `stages.ini` entry, `id 0`, index 0), so `isTutorial()` is true on a new game's Day 1 there (`tools/scenarios/standin_practice_stage.h`, `standin-objects.md`, Tutorial stage). `tutorial_skip`, `tutorial_firsts` and `tutorial_day1` run on it. Forest and Cave stand-ins (DF01, DF16, AC3) are still missing.

- Story-course day end with a sprout still planted (original code): `GameCoreSection::cleanupDayEnd` step 4 stores each sprout for the next visit and kills it, and `PikiHeadItem::doKill` (written for a plucked sprout) moves it from `GameStat::mePikis` to `workPikis` with no Pikmin behind it. `allPikis` and `mapPikis` are unchanged; only the split is off, until the next stage's `GameStat::init`. It runs only on story courses (`isGameCourse`), so the sandbox stages never reached it; the runner's GameStat invariant reports it (formation + free + work 2 above the live Pikmin with two sprouts planted). `tutorial_day1` plucks every sprout first; the quirk itself is not asserted.
- DF15 FinishBoxPush is not stage-gated (only DF14 is); DF30's check is in `PikiNukareState::cleanup`, so the Whistle Pluck path never sets it (read only).
- The stand-in tree could not carry anything before this (`standin-objects.md`): the Pikmin PickLoop motion lacked the KEY_Action0 that ends the lift, the red Onion's boot lacked the effect event that reopens its route way point, and the push box had no collision. Each now has the disc's numbers.
- `PathFinder::findSyncOnyon` (original) walks every simple path of the route graph. On a compiled map with the default 150-unit route grid (`nectar_mapcore`, with diagonals: 81 points on a 1,600-unit map) one carry's route search did not finish in two minutes (sampled: `selectWayOnyon` recursion); the tutorial stage uses a 3 by 3 grid. Maps built with the mapmaker's default grid (custom maps, missions) may hit it on a carry; not checked.

### Findings from `ship_parts` (2026-10-28)

- `getUfoParts(id, true)` does not avoid registration: `findUfoParts` only finds registered parts, and the invisible path writes `parts->mPartVisType`, so an unregistered id is a null dereference. The stand-in tree registers none of the 30 (the earlier "16" counted `pelAnim.bin` shape infos; `registerUfoParts` runs over the `pelMgr.bin` configs of type UfoPart, and the stand-in `pelMgr.bin` has only the 12 pellets). `ship_parts` registers the ids itself with `PlayerState::registerUfoParts`; on the disc all 30 are registered.
- Latent bug, not fixed (game code untouched): `mStagePartsCollected[mStageID]++` on `u8[STAGE_COUNT = 5]` with the sandbox's id `STAGE_TESTMAP` (5) writes one byte past the array, into the first byte of `mPerHourGraph`. The scenario swaps in a valid stage id around each call and asserts the bytes after the array are unchanged.
- `getNextPowerupNumber()` returns `counts[level] - mCurrParts` (parts left to the next level: 5 after the first part, 0 at 30), not the `1,6,12,29,30,30` table that the SP11 row quotes. The scenario asserts the remaining count against the live thresholds.
- Achievements: `getUfoParts` calls `pc_achievements_on_ship_part`, which would save `pikmin_achievements.txt` in the working directory and queue a toast that reads a part icon (`screen/tex/imageNNN.bti`, absent from the stand-in tree, and which one depends on wall-clock time). The scenario blocks achievements with `pc_settings_scenario_set_infinite_day(1)` (one of the cheat reasons) and asserts no file appears.
- `setSeen` replaces the "on" state (2, not 3): at part 25 `Collect15Parts` goes 1 to 2, at part 29 `Collect25Parts` goes 1 to 2.
- Order matters for `happyEndable`: with an optional part taken early, 25 required parts is the 26th part, while `Collect25Parts` is set on the 25th.
